## 1. D6 — Tenant-context derivation mechanism

| Field | Content |
|---|---|
| **Current status** | `DECISIONS.md` D6 record: **DEFERRED — Phase 3** (recorded 2026-09-06, via approved re-scope G-17). Not yet resolved — deferral was itself the decision at Phase 2 time; resolving it is Phase 3's own first job. |
| **Exact decision required** | How does a merchant-console request identify **which tenant** it is operating on, so `TenantContext`'s merchant-path resolver and the tenant-aware `PermissionsGuard` can select the correct `TenantMembership` to check? Concretely: **(a)** host/subdomain only, **(b)** an explicit `X-Active-Tenant` request header that must match one of the caller's `ACTIVE` memberships (else 403), or **(c)** both, with a defined precedence when they disagree. |
| **Recommended option** | **(c) — host/subdomain primary, `X-Active-Tenant` header as an explicit override for a `User` with multiple memberships**, with the header always cross-validated against the caller's actual memberships (never trusted alone). Reasoning: the current merchant console is a single global admin surface (no per-tenant subdomain routing exists yet in the frontend), so a header-based active-tenant selector is needed *now* for any `User` holding >1 membership, while host-based resolution is the long-run mechanism once tenant-specific admin subdomains exist (Phase 5+ platform console work). Both mechanisms are already anticipated in the original D6 question wording (`DECISIONS.md` line 165: "host / subdomain / an explicit `X-Active-Tenant` header"). |
| **Alternatives** | **(a) Host/subdomain only** — simpler, but the current admin console has no per-tenant host routing built, so this would block any `User` with multiple memberships from ever selecting a non-default tenant; effectively unworkable until Phase 5's platform/console work lands. **(b) Header only** — workable today, but gives up the more spoof-resistant host-based signal for tenants that *do* eventually get dedicated admin subdomains, and would need revisiting later anyway. |
| **Security impact** | This is the single highest-leverage decision in Phase 3 (Master Plan §9 SECURITY IMPACT: "context derivation must be unspoofable"). Whichever mechanism is chosen, the header/host value is **only a hint** — the resolved tenant must always be cross-checked against the caller's actual `ACTIVE` memberships server-side, and a mismatch must 403 (verified by a dedicated e2e negative test, spec §14). Choosing (a) alone would remove the spoof surface entirely but at the cost of the console being unusable for multi-tenant `User`s until Phase 5; choosing (b) alone or (c) both requires the cross-validation step to be implemented correctly and tested, or it becomes the exact vulnerability class Master Plan §9 KEY RISKS calls out ("attacker sets `X-Active-Tenant` to another tenant"). |
| **Operational impact** | (c) requires no new infrastructure — it's request-header handling in existing NestJS middleware/interceptor code. No deploy topology change, no new environment variable. Support/debugging burden is slightly higher than (a) alone (two code paths to reason about), but matches how the frontend `authStore`'s planned "tenant switcher" (already scoped for Phase 2/5 per Master Plan §8 FRONTEND IMPACT) would naturally set the header. |
| **Backward-compatibility impact** | No existing session/token shape changes — Phase 2a already loads `memberships` onto every request's `AuthenticatedUser` (see `jwt.strategy.ts`); D6 only decides how one of those memberships becomes "active" for a given request. No re-login, no `tokenVersion` bump, no migration. |
| **What Phase 3 implementation depends on it** | `TenantContext`'s merchant-path resolver (spec §4) cannot be written at all without this decision — it is the literal input to "which membership does this request operate under." `PermissionsGuard` (spec §7) cannot select a membership to check without an active tenant. Every domain-service migration to the scoped Prisma client (spec §11) is downstream of this. |

## 2. D4 — Isolation mechanism: application layer, RLS, or both

| Field | Content |
|---|---|
| **Current status** | Listed in `DECISIONS.md`'s "Decisions from earlier documents NOT recorded here as resolved" table as **OPEN**: *"Doc-level classification 'both'; not owner-ratified. Gates Phase 3."* No full decision record exists yet — unlike D6, D4 has never been given its own `## D4 — …` section. The Master Plan's Phase 3 text (§9) already writes as if "both" were settled ("the tenant-scoped data access path (D4: app-layer + RLS)"), but this is the *document's* proposal, not an owner ratification. |
| **Exact decision required** | Should tenant isolation be enforced by **(i) application-layer scoping only** (a Prisma client extension that injects `where: { tenantId }` into every query), **(ii) Postgres Row-Level Security only**, or **(iii) both**, with app-layer as the primary mechanism and RLS as defense-in-depth? |
| **Recommended option** | **(iii) both, app-layer primary** — matches the Master Plan's own design intent and the general security principle of defense-in-depth for the single highest-consequence bug class in a multi-tenant system (cross-tenant data leak). App-layer scoping alone is easy to bypass by a single missed migration to the scoped client in a new/edited service; RLS alone is easy to bypass by a misconfigured DB role or connection pooler (see P3-D2) and gives worse error messages / harder debugging. Together, a bug in one layer is caught by the other. |
| **Alternatives** | **(i) App-layer only** — simpler to build and reason about, no RLS/pooler compatibility risk (P3-D2 becomes moot), faster to ship, but has *zero* enforcement if a developer ever queries via the raw `PrismaService` and the CI import-allowlist gate has a gap or is bypassed in review. **(ii) RLS only** — strongest guarantee against application-code bugs, but Master Plan §9 KEY RISKS already flags real operational risk (pooler compatibility, `SET LOCAL` semantics, DB-role `BYPASSRLS` status) that must be verified per P3-D2 *before* this is viable at all; also produces less specific error messages (a silently-filtered `0 rows` result instead of an explicit 403/404) which can be confusing to debug and to test. |
| **Security impact** | This decision defines the actual isolation boundary the rest of Phase 3 is built to enforce (Master Plan §9: "the core of invariants 1, 2, 3, 18"). Choosing app-layer-only accepts a known bypass risk (a missed scoped-client migration) mitigated only by a CI lint gate; choosing RLS-only accepts a known misconfiguration risk (superuser/`BYPASSRLS` role, pooler mode) that could silently make RLS a no-op; choosing both minimizes single-point-of-failure risk at the cost of more code and more to verify (P3-D2). |
| **Operational impact** | (i) alone: no infra change. (ii) or (iii): requires verifying the Render-managed Postgres app role is non-superuser/non-`BYPASSRLS` (may require an ops action to change the connection role Render provisions), and requires confirming the connection-pooling mode in use is compatible with per-transaction `SET LOCAL` (PgBouncer transaction-pooling mode is fine for `SET LOCAL`, not for a plain session-level `SET`) — this is exactly P3-D2, and its answer could retroactively constrain this decision (if the role turns out to be `BYPASSRLS` and cannot be changed, RLS is off the table regardless of preference here). |
| **Backward-compatibility impact** | (i) is a pure application-code change, fully backward compatible, no migration. (ii)/(iii) require an additive migration (`ENABLE ROW LEVEL SECURITY` + `CREATE POLICY` on the Phase 1/2a tenancy tables only — spec §12–13) — additive, reversible via `DISABLE ROW LEVEL SECURITY`, no existing data affected, passes the additive-only CI guard (G-10/G-19) as currently written (to be verified once drafted). |
| **What Phase 3 implementation depends on it** | Directly gates spec §12 (schema changes) and §13 (migrations) — if RLS is out of scope, Phase 3 ships **zero** migrations. Also gates whether P3-D2's ops verification work is required at all this phase, and shapes the scoped-Prisma-client design (spec §5): app-layer-only means the scoped client is the *sole* enforcement point and its CI import-allowlist gate becomes the single most safety-critical check in the phase. |

## 3. G-13 — Permission catalogue ratification

| Field | Content |
|---|---|
| **Current status** | `DECISIONS.md` G-13 record: **NOT REQUIRED FOR PHASE 2**, explicitly deferred: *"A G-13-equivalent ratification of the exact permission strings will be required at the start of Phase 3."* That time has arrived — the catalogue itself has not yet been authored (confirmed: `backend/src/auth/permissions/` does not exist in the current tree). |
| **Exact decision required** | Ratify the **exact permission-string catalogue** (e.g. `orders:read`, `orders:transition`, `products:write`, `coupons:write`, `settings:write`, `members:manage`, `payment-account:manage`, …) and the **`TenantRole → Set<Permission>` map** (which of `OWNER`/`ADMIN`/`STAFF`/`VIEWER` gets which permission) as a security artifact — the representation itself (typed constant) is already frozen by P2-D8 and is not re-opened here. |
| **Recommended option** | Draft the full catalogue and role→permission map as a standalone, reviewable artifact (mirroring how G-5 ratified the Phase 1 enum value sets) **before** any `@RequirePermission` decorator is written against it — i.e., ratify the *list*, then implement against the ratified list, not the reverse. A starting proposal (to review, not to treat as decided): `OWNER` gets every permission including `members:manage` and `payment-account:manage`; `ADMIN` gets everything except `members:manage`/`payment-account:manage`/tenant-deletion-class actions; `STAFF` gets read + operational-write (`orders:transition`, `products:write`) but not `settings:write` or `coupons:write`; `VIEWER` gets read-only permissions exclusively. |
| **Alternatives** | Defer catalogue authoring further and ship Phase 3's tenant-context mechanism first, activating `PermissionsGuard` in a later sub-phase — rejected as a recommendation because it would mean landing `TenantContext` and the scoped client without the enforcement layer that gives them purpose, and because Master Plan §9's exit criteria bundle catalogue activation into Phase 3's own completion. A narrower catalogue (fewer, coarser-grained permissions, e.g. just `read`/`write` per domain instead of per-action) is a legitimate alternative shape, trading precision for a smaller initial surface to ratify and test. |
| **Security impact** | Master Plan §8 KEY RISKS names this explicitly as a **privilege-escalation surface**: an over-permissive map (e.g. `STAFF` accidentally granted `members:manage`) is a direct security defect, not a UX bug. Ratification-as-security-artifact (same rigor as G-5) is the mitigation; deny-by-default (no catalogue entry → 403) is the structural backstop for anything the ratification process misses. |
| **Operational impact** | Authoring is a documentation/code exercise with no infrastructure impact. Once ratified, any *future* permission addition or role-mapping change should go through the same ratification discipline (a lightweight version of this same docket process) rather than being added ad hoc in a feature PR — worth stating as a norm alongside the ratification itself. |
| **Backward-compatibility impact** | None — no existing route, session, or token is affected until the catalogue is wired to `@RequirePermission` (spec §8's separate mechanical-swap step). Ratifying the catalogue in isolation (spec §17 step 3) is fully inert until that later step. |
| **What Phase 3 implementation depends on it** | `PermissionsGuard` (spec §7) has nothing to check against without a ratified catalogue; the entire `@Roles` → `@RequirePermission` mechanical swap (spec §8, 19 call sites) cannot be written correctly without knowing which permission string replaces which `@Roles(Role.ADMIN)` call. This is the second decision (after D6) with the widest downstream blast radius in the phase. |

## 4. P3-D1 — Rollout / advisory-flag location

| Field | Content |
|---|---|
| **Current status** | **New — not previously asked.** Raised in `PHASE-3-START-GATE-AND-IMPLEMENTATION-SPEC.md` §2 as a gap: Master Plan §9 specifies a per-module `TENANT_ENFORCEMENT[module] = 'advisory' \| 'enforced'` flag but does not say where that flag's value is stored or how it's changed. |
| **Exact decision required** | Where does the per-module advisory/enforced state live: **(a)** a code constant (requires a deploy to change), **(b)** an environment variable per module (requires a redeploy/restart to change, but no code change), or **(c)** a DB-backed or feature-flag-service config (changeable at runtime, no deploy or restart)? |
| **Recommended option** | **(b) — environment variables**, one per module (e.g. `TENANT_ENFORCEMENT_ORDERS=enforced`), read once at boot. Reasoning: this is a security-relevant, infrequently-changed setting (Master Plan's own rollout plan is "≥1 week advisory observation, then flip") — a full runtime feature-flag system (c) is more machinery than the rollout cadence justifies, while a code constant (a) makes the "instant rollback without a deploy" property from spec §16 untrue (a deploy would still be needed to *build* the flag change, only not to write code). Env vars match the project's existing configuration pattern (`ConfigService<AppConfig, true>`, already used throughout `backend/src/common/config/`) and support a restart-only rollback, which is fast on the current Render topology without being a new subsystem. |
| **Alternatives** | (a) code constant — simplest, but contradicts the "flip back without a deploy" rollback property spec §16 assumes. (c) DB-backed/feature-flag service — fastest possible rollback (no restart needed), best long-term fit if the platform later needs dynamic per-tenant or gradual-percentage rollout, but introduces a new subsystem (or a new table + caching layer) purely for this phase's needs, which is disproportionate machinery for a mechanism intended to be temporary (Phase 4 is expected to flip every module to `enforced` permanently, retiring the flag). |
| **Security impact** | Low direct security impact from the storage choice itself, but the *operational speed of rollback* it enables is a mitigation for the KEY RISKS Master Plan §9 names (a query path that bypasses the scoped client, discovered via advisory-mode breadcrumbs) — slower rollback (a) is a weaker mitigation than faster rollback (b) or (c). |
| **Operational impact** | (b) requires an ops action (env var change + restart) per flip, on every environment (staging, then production) — a small, well-understood operational step already familiar from this project's existing `ConfigService` usage. No new tooling, dashboards, or access-control surface to build, unlike (c). |
| **Backward-compatibility impact** | None regardless of choice — this is new machinery with no prior state to be compatible with. All modules should default to `advisory` when the env var is unset, so a missing/misconfigured var fails toward "logs, doesn't break," not toward "throws in production." |
| **What Phase 3 implementation depends on it** | Affects the `TenantContext`/scoped-client wiring (spec §11 step 7) and every module-migration commit (spec §19 item 4) — each module's migration PR needs to know what config surface to read the flag from. Does not block *starting* implementation (module code can be written flag-agnostic and wired to whichever mechanism is chosen last), but should be settled before the first module migration PR to avoid rework. |

## 5. P3-D2 — RLS DB-role and connection-pooler compatibility

| Field | Content |
|---|---|
| **Current status** | **New — not previously asked; an ops-verification item, not a design preference.** Raised in `PHASE-3-START-GATE-AND-IMPLEMENTATION-SPEC.md` §2, sourced directly from Master Plan §9 INFRASTRUCTURE IMPACT: *"RLS requires the DB role used by the app to be non-superuser and non-`BYPASSRLS`… REQUIRES DECISION-minor / ops"* and *"`SET LOCAL` per transaction: verify the pooler… is compatible."* Nothing has been checked against the actual Render Postgres instance yet — this spec/docket process did not access production, per the standing constraint on this task. |
| **Exact decision required** | This is not a preference decision but a **fact-finding + go/no-go gate**, to be answered by inspecting the actual Render-managed Postgres configuration (read-only, via the D8-authorized access pattern already established, or via the Render dashboard directly by the ops owner): **(1)** is the application's DB role a superuser or does it have `BYPASSRLS`? **(2)** is a connection pooler in front of the database, and if so, does it operate in a mode (session vs. transaction pooling) compatible with per-transaction `SET LOCAL`? |
| **Recommended option** | Ops owner checks both facts directly against the Render dashboard/`psql` (read-only: `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;` and confirming Render's connection topology) **before** D4 is finalized, since a "yes, bypasses RLS" or "pooler incompatible" answer here removes RLS as a viable option and would flip the D4 recommendation from "both" to "app-layer only." Do not schedule this as parallel, independent work — sequence it immediately before or alongside the D4 decision. |
| **Alternatives** | Skip this verification and proceed with app-layer-only isolation (D4 option i) — a legitimate alternative if the owner prefers to avoid the ops investigation entirely; this makes P3-D2 moot rather than answering it. Alternatively, provision a dedicated non-superuser, non-`BYPASSRLS` role specifically for the application if the current role fails the check — an ops remediation rather than a design alternative. |
| **Security impact** | If RLS is adopted (D4) without this verification and the role turns out to have `BYPASSRLS`, RLS policies would be **silently inert** — the worst possible outcome, since the team would believe a defense-in-depth layer exists when it does not. This makes the verification a hard precondition for claiming RLS as part of the isolation mechanism, not an optional nice-to-have. |
| **Operational impact** | A one-time, read-only diagnostic check (no production write). If the role must change, that is a real ops action (Render role/permission configuration) with its own small risk of connection-string/credential rotation — should be tested in a non-production environment first if it comes to that. |
| **Backward-compatibility impact** | None from the check itself. If a role change is required, existing connections/credentials would need rotation — the same class of careful, D8-style verified-backup-first operational discipline already established in this project's Phase 2 D8 process should apply if this remediation is ever needed. |
| **What Phase 3 implementation depends on it** | Directly gates whether D4 can honestly include RLS at all. Also gates spec §13's conditional migration (RLS-enabling migration only exists if this check passes) and spec §18's acceptance criterion "(if D4 = RLS or both) RLS enabled on tenancy tables; DB-role and pooler compatibility confirmed." |
